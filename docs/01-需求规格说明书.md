## 1. 项目概述

### 1.1 背景
传统 QA 流程依赖人工编写和维护测试用例、执行回归、分析日志及提交缺陷。随着产品复杂度增长，测试覆盖、脚本维护、失败归因和测试资产复用的成本持续增加。

QA-Swarm 已提供 AI Agent 驱动的基础 QA 闭环，包括应用探索、测试生成、测试执行、失败分诊、安全检查、性能检查和报告。AQAOS 在其基础上演进为支持多项目、多应用、多模型、持久化工作流、Web/API 执行、独立 Bug 验证和长期质量知识管理的自托管平台。

### 1.2 产品愿景
构建一个完整的 AI QA 团队，让 AI 承担传统软件测试团队的大部分工作。AI 不是简单地生成测试脚本，而是像一个真正的 QA 团队一样工作：

- 理解产品需求和业务逻辑。
- 自主探索 Web 和 API 应用。
- 自主制定测试策略。
- 自主设计测试用例。
- 自主执行测试。
- 主动寻找边界条件和异常路径。
- 识别真正的产品缺陷。
- 独立验证自己发现的 Bug。
- 生成可复现的缺陷报告。
- 将测试经验沉淀为长期知识。
- 根据历史测试结果持续优化测试策略。

### 1.3 产品定位
AQAOS 是一个完整的 AI QA 团队平台，而非 AI 测试脚本生成器。

- 产品核心：自主 QA 团队。
- 技术核心：可靠执行引擎。
- 差异化竞争力：独立 Bug 验证 + 长期质量记忆。

项目不是多个 Agent 的简单拼接，而是一个能够持续工作的 AI QA 组织。核心能力划分为：

| 能力域 | 内容 |
|---|---|
| QA Intelligence | 产品理解、测试规划、探索和决策 |
| QA Orchestration | Agent 管理、工作流编排和恢复 |
| QA Execution | Web、API 执行与环境编排 |
| QA Knowledge | 产品、测试、缺陷、证据和反馈知识资产 |

### 1.4 产品形态
独立的 AI QA 平台，而不是单独的测试框架、CLI 工具或某个自动化测试工具的插件。平台由以下部分组成：

1. Web 管理后台。
2. AI Agent 管理中心。
3. 自主测试编排引擎。
4. Web 与 API 测试执行引擎。
5. 多模型路由系统。
6. Bug 智能分析系统。
7. 测试知识和长期记忆系统。
8. 测试报告与质量分析系统。
9. 测试环境管理（含 Docker Compose 编排）。
10. 测试用例库与维护管理。
11. API 和 MCP 接口。
12. 完整的自托管部署能力。
13. CLI 客户端（复用 QA-Swarm CLI，供个人开发者触发 Run 与查看结果）。

### 1.5 范围边界
本项目范围：Agent 编排、Web/API 测试、安全与性能检查、Bug 验证、回归资产、模型管理、长期记忆、测试环境管理（含 Docker Compose 编排）、测试用例管理、测试数据管理、触发与调度（定时/CI/事件）、外部缺陷单集成、Dashboard、REST API、MCP、CLI、自托管部署和可观测性。

暂不承诺：Mobile（Android/iOS）测试（暂缓，待后续阶段重新评估）；替代人工质量签字；未经授权测试第三方系统；默认在生产环境执行破坏性操作；自动修改业务代码并直接发布；训练通用基础模型。

## 2. 目标用户与使用场景

### 2.1 目标用户
- 软件研发团队。
- QA 测试团队。
- SaaS 产品团队。
- 企业内部研发平台团队。
- 希望建设 AI 自动化测试体系的组织。

### 2.2 用户角色

| 角色 | 职责 |
|---|---|
| System Admin | 部署、全局配置、模型、Worker、安全策略 |
| Project Admin | 项目、应用、环境、成员、预算和策略 |
| QA Engineer | 创建 Run、审核用例和 Bug、管理回归集 |
| Developer | 查看缺陷、复现步骤、证据和回归结果 |
| Viewer | 只读查看任务、报告和质量趋势 |

### 2.3 核心使用场景

**场景 A：新应用自动测试**
用户只需要提供应用 URL、测试账号和目标。AI 自主探索应用，理解页面和业务流程，生成测试计划并执行测试。

**场景 B：已有应用全面测试**
用户选择一个已有应用，要求 AI 执行全面 QA。AI 根据历史知识和当前应用状态，执行功能、接口、异常、安全和性能测试。

**场景 C：发现并验证 Bug**
AI 在测试过程中发现异常，自动分析根因，通过独立会话重新执行，确认是否是真实缺陷。

**场景 D：持续回归测试**
应用发生变化后，AI 根据历史测试资产、产品变更和已知 Bug 自动调整测试计划，执行回归。

**场景 E：多个应用同时测试**
平台同时管理多个应用，多个 Agent 团队并行工作，统一监控资源、模型成本和测试结果。

**场景 F：环境一键拉起**
用户为应用配置 Docker Compose 测试栈。平台负责启动、健康检查、就绪后执行测试、测试后停止与清理，无需人工准备环境。

**场景 G：无人值守持续质量**
CI 流水线在 PR/MR 创建、部署完成后自动触发 QA Run；平台按 Cron 定时执行夜间全量回归。结果回写 PR check，确认 Bug 推送外部缺陷单，外部修复回流后自动触发回归验证。

### 3.1 Agent 管理中心

Agent 团队角色（16 个；Mobile Tester 暂缓引入）：

| Agent | 核心职责 |
|---|---|
| QA Manager | 统筹测试任务和 Agent 团队 |
| Product Analyst | 理解产品和业务逻辑 |
| Planner | 制定测试计划 |
| Explorer | 自主探索应用 |
| Test Architect | 设计测试策略 |
| Test Generator | 生成测试用例 |
| Web Tester | 执行 Web 测试 |
| API Tester | 执行 API 测试 |
| Security Tester | 执行安全测试 |
| Performance Tester | 执行性能测试 |
| Triage Agent | 分析测试失败 |
| Bug Verifier | 独立验证 Bug |
| Root Cause Analyst | 分析根因 |
| Regression Agent | 维护回归测试 |
| Self-Healing Agent | 修复测试脚本和 Locator |
| Reporter | 生成测试报告 |

Agent 按实现形态分三类（详见 SDD 6.3），不全部会话化，避免 Token 浪费与不可控：

| 类型 | 实现方式 | 角色 |
|---|---|---|
| 会话型 | 纯推理决策，完整 Claude Code 会话 | QA Manager、Planner、Product Analyst、Test Architect、Triage Agent、Root Cause Analyst |
| 混合型 | Claude Code 会话驱动 MCP 工具执行 | Explorer、Test Generator、Bug Verifier、Self-Healing Agent、Regression Agent、Reporter |
| 程序型 | 确定性 Runner，LLM 仅做事后分析 | Web Tester、API Tester（执行核心）、Security Tester（确定性检查）、Performance Tester（测量） |

Agent 自主性要求：

- Agent 可以动态创建任务。
- Agent 可以自主调用工具。
- Agent 可以将任务委派给其他 Agent。
- Agent 可以并行工作。
- Agent 可以根据执行结果调整计划。
- Agent 有独立运行状态和预算。
- Agent 可以暂停、恢复和终止。
- Agent 的所有操作可追踪。
- 支持人工介入和审批。

**核心目标：尽可能减少人工参与，但不能绕过权限、安全和审批边界。**

Agent 运行时基于 Claude Code（Claude Agent SDK）实现：

- Agent 角色由系统提示词 + MCP 工具白名单 + 模型配置定义。
- 工具调用统一经平台 MCP Server 执行。
- 任务委派通过 Claude Code 子代理（subagent）完成。
- 高风险操作经 hooks 与平台审批策略联动。
- Agent 运行于 Claude Code 沙箱与 Worker 容器隔离之中。

### 3.2 自主探索引擎

这是整个产品最重要的能力之一。AI 不能只按照已有测试用例执行，还必须具备自主发现应用功能的能力。

Web 探索：

- 自动访问页面。
- 识别页面结构。
- 识别按钮、表单和交互元素。
- 发现页面跳转。
- 发现隐藏页面。
- 识别登录和权限状态。
- 识别用户流程。
- 收集 API 请求。
- 构建页面关系图。

API 探索：

- 自动解析 OpenAPI。
- 发现 Endpoint。
- 分析参数和响应。
- 推断接口依赖。
- 识别状态变化。
- 探索异常输入。
- 识别潜在权限问题。

探索约束：Explorer 必须执行授权域名检查、页面去重、最大页面数/深度/时间/预算限制，记录页面角色、元素、链接、网络观察和证据。探索事实需区分 confirmed、inferred、unknown。

**探索最终必须生成结构化产品知识，而不是只输出一段自然语言总结。**

### 3.3 测试设计中心

AI 应当根据产品理解自动制定测试策略。

测试类型：

- Smoke Test
- Functional Test
- Boundary Test
- Negative Test
- Integration Test
- Regression Test
- Authorization Test
- Security Test
- Performance Test
- Exploratory Test
- State Transition Test
- Compatibility Test

Compatibility Test 本期范围为浏览器矩阵：Chromium、Firefox、WebKit（Safari 内核）。Smoke 用例默认仅 Chromium 执行；Compatibility 用例在矩阵全浏览器执行，并发受 Browser Slot 限制。

测试用例字段：

| 字段 | 说明 |
|---|---|
| ID / 标题 | 唯一标识与用例名称 |
| 测试目标 | 用例验证的业务意图 |
| 前置条件 | 执行前必须满足的状态 |
| 测试数据 | 输入数据与构造方式 |
| 执行步骤 | 可复现的操作序列 |
| 预期结果 | 断言与业务预期 |
| 风险等级 | 失败影响评估 |
| 优先级 | 执行顺序权重 |
| 所属平台 | Web / API |
| 业务模块 | 归属功能域 |
| 覆盖范围 | 覆盖的页面/接口/流程 |
| 清理策略 | 执行后的数据清理 |
| 版本 | 用例版本号 |

### 3.5 Bug Intelligence

不能把测试失败直接当成 Bug。系统必须区分：

| 分类 | 枚举值 | 说明 |
|---|---|---|
| 真实产品缺陷 | `product-bug` | 应用本身错误 |
| 测试脚本错误 | `test-bug` | 测试自身缺陷 |
| 环境问题 | `environment` | 基础设施故障 |
| 网络问题 | `network` | 网络抖动或中断 |
| 不稳定测试 | `flaky` | 非确定性失败 |
| 模型误判 | `model-error` | AI 判断错误 |
| 未知异常 | `unknown` | 证据不足 |

核心功能：

1. 自动发现。
2. 自动分类。
3. 自动去重。
4. 自动评估严重程度。
5. 自动生成复现步骤。
6. 独立 Agent 重新验证。
7. 根因分析。
8. 证据关联。
9. 自动生成回归用例。

验证要求：发现 Agent 与 Verifier 必须职责分离。验证需使用独立会话重新执行、记录尝试次数、复现次数、置信度、原因和独立证据。不能只凭模型判断确认 Bug。

### 3.6 长期记忆和知识系统

每个应用拥有长期知识库。记忆包括：

- 产品结构。
- 页面关系。
- API 结构。
- 业务流程。
- 用户角色。
- 历史测试用例。
- 历史 Bug。
- 历史失败。
- 修复经验。
- 测试反馈。

目标：让 AI 每次执行测试时，不必重新理解整个应用。记忆按 Organization/Project/Application 隔离，每条记忆携带来源 Run、版本、置信度和时间。

### 3.7 多模型自动路由

模型管理不能简单配置一个默认模型。系统根据任务自动选择模型：

| 任务 | 模型能力 |
|---|---|
| 简单页面分类 | 低延迟模型 |
| 页面和业务理解 | 强推理模型 |
| 测试用例生成 | 推理 + 结构化输出 |
| 页面截图分析 | Vision 模型 |
| Bug 根因分析 | 强推理模型 |
| 报告生成 | 高性价比模型 |
| 向量记忆 | Embedding 模型 |

支持 Provider：OpenAI、Anthropic、Gemini、DeepSeek、Qwen、Ollama、vLLM 及 OpenAI-Compatible Provider。

自动路由必须考虑能力、延迟、价格、可用性、数据敏感级别和预算，而不是只选择最便宜的模型。模型名称必须配置化，不允许硬编码在 Agent 业务逻辑中。

Agent 推理（Claude Code 会话）默认使用 Claude 系列（Anthropic API / Bedrock / Vertex，可经网关代理纳入统一预算与审计）；其余任务（Embedding、简单分类、报告等）按上表路由到相应 Provider。

## 4. 核心业务流程

### 4.1 应用接入
创建项目 → 创建应用 → 配置环境（external 或 Docker Compose 栈）→ 配置 URL/OpenAPI → 配置凭据引用 → 连通性与权限校验 →（可选）平台拉起 Compose 环境并健康检查 → 产品分析 → Explorer 探索 → 形成初始产品知识模型。

### 4.2 自主 QA
创建 QA Run → QA Manager 统筹 → Planner 分析目标 → Product Analyst 加载产品知识 → Explorer 探索 → Test Architect 规划 → Test Generator 生成用例 → Orchestrator 分配 Agent → Web/API/Security/Performance 执行 → Evidence Collector 收集证据 → Triage 分析 → Bug Verifier 独立验证 → Root Cause Analyst 分析根因 → Regression Agent 生成候选用例 → Reporter 输出报告 → Memory 更新。

### 4.3 Bug 生命周期
`candidate → triaging → verifying → verified/rejected → open → fixed → regression_passed`
若回归失败则进入 `reopened`。每次状态变更必须记录操作者、时间、原因和证据。

### 5.1 应用与环境要求
应用配置至少包括名称、类型、基础 URL、OpenAPI 地址、版本、允许域名和凭据引用。环境必须独立配置 URL、账号引用、网络策略、执行权限和数据清理策略。Production 默认只读，且禁止由平台拉起或销毁。

应用建模规则：Application.platform 为单值（web 或 api）。web 型应用可同时注册 OpenAPI 地址，此时 Run 的 platforms 可包含 api（前端走 Web Runner、接口走 API Runner）；api 型应用必须提供 OpenAPI。TestRun.platforms 必须是所选应用能力集合的子集。

### 5.2 测试环境管理要求
环境支持两种供给方式：

- **external**：被测应用已在外部运行，仅配置 URL 与凭据引用。
- **docker-compose**：由平台编排拉起被测应用栈。

Docker Compose 环境要求：

- 绑定 compose 文件引用（仓库路径或对象存储）与变量模板。
- 平台负责 up/down/重启与销毁；健康检查就绪前不得进入测试。
- 环境栈状态机：`unprovisioned → provisioning → ready → stopped`，失败进入 `failed` 并保留诊断日志。
- 同一环境同时仅允许一个活动栈（互斥锁）。
- 资源限额（CPU/内存）与清理策略，防止栈残留。
- 凭据以引用注入容器环境变量，不落盘、不进日志。
- 镜像与网络出口需通过白名单校验。

### 5.3 测试用例管理要求
用例是受管理的长期资产，不是一次性生成物：

- **生命周期**：`draft → reviewed → active → deprecated`。AI 生成用例默认 draft，经人工审核后转为 active 才进入执行计划与正式回归集。
- **版本管理**：每次修改生成新版本，可查看差异、回溯历史版本。
- **来源标记**：区分 AI 生成与人工编辑，修改记录操作者。
- **启用/禁用与标签**：禁用用例不再执行；支持平台/类型/业务模块/标签筛选。
- **flaky 标记**：连续判定 flaky 的用例进入隔离，仍执行但不阻塞 CI。
- **关联追溯**：用例与 Run 结果、Bug、回归集关联，可查询"某 Bug 由哪些用例覆盖"。
- **导入导出**：JSON/CSV 格式，用于迁移与评审。
- **用例与执行脚本分离**：用例库是唯一事实源；执行脚本（Playwright spec / Schemathesis 配置）由 Test Generator 从用例渲染生成并以指纹绑定，同一用例可对应多浏览器/多环境脚本。脚本手工修改必须回写用例并升版本，否则标记漂移并阻止进入回归集。

### 5.4 测试数据管理要求
- 数据集（data_sets）定义业务实体样本（账号、订单、支付、边界值集合），带 PII 脱敏规则。
- 用例引用数据集字段；Boundary/Negative/Authorization 用例消费数据集变体。
- 环境支持数据播种（seed）与重置（reset）；Run 可声明执行前重置，保证可复现。
- 数据集变更必须触发受影响用例重审，不允许静默失效。

## 6. 自主性等级

自主性是 AQAOS 的第一核心竞争力，设计为逐级提升：

| 等级 | 能力 | 人工参与 |
|---|---|---|
| L1 | AI 辅助生成测试 | 高 |
| L2 | AI 自动执行已有测试 | 中高 |
| L3 | AI 自主探索和生成测试 | 中 |
| L4 | AI 自主发现、验证、回归 | 低 |
| L5 | AI 持续理解产品并自主优化 QA | 极低 |

最终目标：L5。

但 L5 不等于无限制地自主操作。生产环境、支付、删除数据和安全测试等高风险行为仍然需要策略限制或审批。

阶段对应：第一阶段交付 L3；第三阶段交付 L4；第四阶段交付 L5；第二阶段为生产化加固，不提升自主性等级。调度与触发（FR-026）是 L4/L5 无人值守运行的必要基础。

## 9. 验收标准

1. 可自托管部署并完成健康检查。
2. 项目、应用和环境间数据隔离有效。
3. Web 和 API 端到端测试可执行。
4. 测试环境支持 Docker Compose 一键拉起；健康检查就绪后方可执行 Run。
5. 候选 Bug 有独立验证记录。
6. 证据可追溯且校验 SHA-256。
7. Worker 重启后工作流能恢复。
8. 模型预算耗尽时停止或降级，不无限调用。
9. 高风险操作被策略拦截或要求审批。
10. 测试用例可查看、编辑、版本回溯；AI 生成用例经人工审核后进入正式用例库。
11. 20–50 个活跃逻辑 Agent 的目标并发通过压力测试；该指标须在目标硬件上基准验证。
12. Run 完成、Bug 确认和审批请求可触发通知（SSE + webhook）。
13. Nightly 定时 Run 与 CI 触发 Run 可无人值守执行，结果回写 PR check。
14. 确认 Bug 可推送外部缺陷单（Jira/GitHub），外部标记 fixed 自动触发回归验证。
15. 可统计误报率、Bug 采纳率、模型误判率；人工反馈进入 Feedback Memory。
