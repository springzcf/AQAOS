## 2. 核心 Domain Model

```ts
interface Application {
  id: string;
  projectId: string;
```

## 3. Agent Contract

```ts
interface AgentContext {
  runId: string;
  applicationId: string;
  environmentId: string;
  objective: string;
  budget: AgentBudget;
  permissions: string[];
  traceId: string;
  signal?: AbortSignal;             // 运行时对象：暂停/恢复/终止传导，不进 wire 契约
}

interface Agent {
  readonly role: AgentRoleId;        // 十六角色规范 id（SRS 3.1）
  readonly version: string;
  execute(context: AgentContext, input: AgentInput): Promise<AgentResult>;
}
```

支撑类型（V1.7 增补内联定义，实现：packages/domain/src/agent.ts；wire 校验只覆盖可序列化字段，signal 由运行侧注入）：
```ts
interface AgentBudget {
  maxTokens: number;
  maxModelCostUsd: number;
  maxToolCalls?: number;
  maxDurationSeconds?: number;
}
interface AgentInput {
  kind: string;                     // 输入形态标记（explore/strategy/steps…）
  payload: unknown;
}
```

所有 Agent 必须：
- 校验输入和输出 Schema。
- 通过上下文获取授权，不自行扩权。
- 通过 Model Gateway 调模型。
- 通过 Tool Gateway 调工具。
- 返回结构化状态、证据引用和用量。
- 支持超时、取消和幂等。
- 不把大文件写入共享状态。

### 3.1 Claude Code 运行时映射

Agent 实现载体为 Claude Agent SDK 会话（Agent Worker 内 headless 运行）。契约映射：

| 契约项 | Claude Code 实现 |
|---|---|
| AgentContext | SDK 会话选项：系统提示词（角色定义）、allowedTools（MCP 工具白名单）、model、会话级预算上限、AbortSignal |
| Agent.execute | Temporal Activity 内启动 SDK 会话，流式收集消息与工具调用；工具经平台 MCP Server 执行 |
| 任务委派 | SDK 子代理（subagent）或 Temporal 子工作流；输出仍受统一 Schema 校验 |
| 人工审批 | PreToolUse hook 拦截高风险工具调用 → approval_requests，等待期间 Activity 挂起 |
| AgentResult | 会话结构化输出解析；校验失败按 partial 处理 |
| 用量与预算 | SDK usage（Token、时长、费用）写 model_invocations 并计入 Run 预算 |

客户端白名单（allowedTools）是第一层限制；服务端身份、权限与预算校验是最终强制层。

### 3.2 agent_definitions 会话选项契约（T-E02-02）

agent_definitions.config JSONB（zod 同源，@aqaos/domain AgentDefinitionConfigSchema）承载非提示词会话配置：model（缺省 worker 默认模型，E03 Model Gateway 上线前直传）、allowedTools（MCP 工具白名单）、maxTurns、effort、persistSession（缺省 false：headless 一次性会话；QA Manager 多轮随 T-E02-05 打开）。行形状 = AgentDefinitionRecord（id/name/version/promptVersion/config/enabled + prompt 本体随行携带，name 必须是十六角色规范 AgentRoleId，prompt 存储版本化随 T-E02-04）。

运行时映射基线（workers/agent 基座，两段纯函数 toSessionSpec/toSdkOptions）：

- **隔离**：内建工具清空（tools: []——AQAOS agents 的工具一律经平台 MCP Server）；strictMcpConfig + settingSources: [] 忽略 .mcp.json/用户/项目/CLAUDE.md 文件系统配置；env 整体替换并注入 CLAUDE_AGENT_SDK_CLIENT_APP 宿主标识；
- **权限失闭**：无审批桥时 permissionPrompts=none（任何需要提示的工具调用立即拒绝）；提供 canUseTool 审批桥时 default 模式路由 approval_requests（T-E03-06 接线）；
- **预算分轨**：成本走 SDK 原生 maxBudgetUsd（= AgentContext.budget.maxModelCostUsd，超限 error_max_budget_usd 终态）；token（口径 input+output）/工具调用数/时长由包装层逐帧计量熔断；外部 AbortSignal（暂停/恢复/终止传导）与超时汇入同一 AbortController；
- **计量口径**：以 result.modelUsage（逐模型累计，含子代理与边链调用）为唯一记账口径——result.usage 仅主循环且逐轮，不得用于记账；每轮 result 触发 usage 回报，终值随会话终态（completed/failed/max-turns/budget-exceeded/aborted + 熔断来源）返回，T-E02-13 落 model_invocations。

### 3.3 agent_definitions 版本化与回滚契约（T-E02-04）

agent_definitions 是 append-only 版本流水：**行创建后不可变**（无 UPDATE/DELETE 路径），prompt 变更 = 追加新行，回滚 = 追加复制行，历史永不改删。DB 层 UNIQUE(name, version) 兜底并发（应用层分配行序号）。

- **双轨版本**：`version` = 行序号（整数串，同 name 单调 +1，管理 API 分配）；`prompt_version` = prompt 内容语义标签（`主.次.修订` semver 文本，随行携带）。二者正交：行序号定位历史，标签标识 prompt 内容代次。
- **核心不变量**：同一 name 下，相同 promptVersion ⟹ 相同 prompt。推论：prompt 变更必须携带新标签（复用旧标签于不同内容 → 400 PROMPT_VERSION_REUSED）；回滚复制旧行 (prompt, prompt_version) 成对落新行，天然合规。
- **空转拒绝**：候选与最新行内容全等（prompt/config/enabled，标签不计）→ 400 NO_CHANGE——流水上不落无信息量的行（含"回滚到最新版"）。
- **列结构**（0007 迁移）：`prompt TEXT NOT NULL`（§3.2 遗留落位）+ `created_at TIMESTAMPTZ NOT NULL DEFAULT now()` + `created_by UUID → users(id) ON DELETE SET NULL`（种子行 NULL）+ (name, created_at DESC) 索引。
- **16 角色基线种子**：`ROLE_PROMPT_BASELINES`（@aqaos/domain agent-prompts.ts 单一事实源，§4.1–4.16 职责 → 五段式系统提示词：身份/使命/工具/纪律/产出）；种子行 version=1、prompt_version=0.1.0；config.allowedTools 基线 = 角色授权（§9 矩阵）∩ 当前已实现注册表工具（SDK 名单形态 `mcp__aqaos__*`）——白名单只暴露真实可调用的工具，服务端矩阵仍是最终强制层。
- **管理面 API**（apps/api）：GET /api/v1/agent-definitions（每角色最新版，member 读）；GET /api/v1/agent-definitions/:name/versions（全版本历史新→旧，member 读）；POST /api/v1/agent-definitions（追加新版本，admin+Idempotency-Key，策略内核 @aqaos/domain checkPromptVersionPolicy 纯函数）；POST /api/v1/agent-definitions/:name/rollback（body {toVersion}，admin，复制成对内容 + enabled=true，目标行缺失 404）。变更类请求经审计中间件自动留痕（create/denied；路由模板去参段得 resource_type，回滚路由为 agent-definitions/rollback）。
- **版本比对**：`diffAgentDefinition`（prompt/promptVersion/config/enabled 逐字段，config 深比较键序无关）与 `comparePromptVersions`（semver 三元组数值序）为纯函数，供管理面、T-E02-05 QA Manager 多轮与展示层消费。

### 3.4 QA Manager 统筹契约（T-E02-05）

QA Manager 是会话型控制面：单条 headless 会话（runQaManagerSession）承载"委派面 + 派发闸门 + 可观测投影 + 多轮续会"四层语义，统筹引擎在 workers/agent qa-manager.ts。

- **委派面**：toSdkSubagent/toSdkAgents 把子代理 AgentDefinitionRecord（§3.2/§3.3 最新启用版）映射为 SDK `Options.agents`（key=角色 id；prompt/工具白名单/模型/maxTurns 逐代理自持，omitClaudeMd=true 隔离宿主指令）。模型经 SDK **Agent 内建工具**委派（sdk.d.ts BUILTIN_TOOL_NAMES 规范名；'Task' 为 LEGACY_TOOL_NAME_ALIASES 旧名），前台串行/后台并行由模型决策。**委派工具必须在 tools 里单独放开**：基线 tools:[] 清空全部内建工具时子代理不可达（live 实证：缺失时模型会"叙述"委派而非真实调用——tools = [SDK_DELEGATION_TOOL] 当且仅当 agents 存在）。
- **派发闸门**（createDispatchGate，canUseTool 桥，验收"预算超限停止派发"）：token（input+output）或成本达限 → 拒绝**一切**工具调用（含 Agent 委派）并给出"停止派发、就地收尾"理由——模型收尾而非硬杀（硬熔断仍由包装层 token/工具/时长 abort + SDK 原生 maxBudgetUsd 双保险）；预算判断数据源 = 会话累计用量（modelUsage 含子代理）。审批 seam（DispatchApproval：toolName+input → boolean）路由 T-E03-06 approval_requests；缺省放行，服务端权限矩阵仍是最终强制层。
- **可观测投影**（验收"多 Agent 并行委派可观测"）：SDK 任务生命周期 system 消息投影为 QaTaskEvent 流——task_started（委派实例诞生，subagent_type=角色 id）/ task_updated（**状态在 patch.status**，live 实证非顶层）/ task_progress 与 task_notification（usage/摘要观测，不改状态）。QaPlanTracker 把事件流按 subagent_type FIFO 绑定落到结构化 QaPlan（@aqaos/domain qa-plan.ts：任务 DAG 校验含环检测/就绪集/失败传导 skipped 闭包/进度聚合），onTaskEvent 回调供 Run Registry（T-E02-12）与 SSE 推送消费。
- **多轮/Query 控制面**：编排器强制 persistSession=true（可恢复是控制面前提）；resumeQaManagerSession 以 sessionId 续会（SDK Options.resume），进度查询/计划调整/取消指令作为后续轮次 prompt 输入；暂停/终止 = 外部 AbortSignal 中断（终态 aborted），恢复 = 续会——DAG 状态由调用方持有跨轮不丢。

### 3.5 Planner 计划契约（T-E02-06）

Planner 是首个**结构化产出**角色：会话最终消息经 SDK `Options.outputFormat`（json_schema）强制为 PlannerPlan JSON（SDK 原生结构化输出重试，`result.structured_output` 承载），平台侧再过 `PlannerPlanSchema` 解析 + `validatePlannerPlan` 合同校验（验收"输出结构化计划过 Schema 校验"）。JSON Schema 由 zod 契约单源生成（zod-to-json-schema，`PLANNER_PLAN_JSON_SCHEMA`），形状与 zod 永不漂移。

- **PlannerPlan 形状**：objective（解析后的可测目标）/ platforms（web|api）/ testTypes（十二类测试意图，可空）/ agents（参与角色集）/ budget（预算估算）/ tasks（任务 DAG）/ assumptions（显式假设 = 给 Product Analyst 的问题清单）。
- **PlannerTask = QaTask + 必填规划字段**：priority 必填、risk（low|medium|high）、acceptance（验收条件文本）。plannerPlanToQaPlan 提取 tasks 即得运行侧 QaPlan（规划期字段在 QaTask 上降级为可选元数据，运行投影只看 id/role）。
- **合同校验**（validatePlannerPlan）：DAG 结构复用 validateQaPlan（重复 id/悬空依赖/环）+ 选角一致性（任务角色 ⊆ agents，`TASK_ROLE_NOT_SELECTED`；选而不用 `AGENT_UNUSED`——选了不委派是规划浪费）+ 预算上限（估算不得超过 Run 预算 cap，`BUDGET_EXCEEDS_LIMIT`——"超预算的计划是计划的缺陷"）。
- **prompt v2（迁移 0008）**：append-only 版本化的首次实战——planner 产出通道从叙述式 AgentResult 升级为 PlannerPlan JSON，追加 version=2 行（prompt_version=0.2.0），v1 行原样保留，latest 切 v2。种子单一事实源 `plannerPlanDefinition()`（agent-prompts.ts，与 0007 同模式）。
- **会话运行器**（workers/agent planner.ts）：runPlannerSession 组装规划轮输入（目标 + 预算上限 + 可选产品知识摘要 + 16 角色名单 + 输出契约重申）→ 结构化产出双校验；PlannerOutcome 契约：`plan` 存在 ⟺ schema + 合同校验全通过，否则 `issues` 携带阻断原因（SESSION_FAILED/PARSE_FAILED/合同问题）供重规划反馈。structured_output 缺席时回退 resultText JSON 解析（容错）。

### 3.6 Product Analyst 知识契约（T-E02-07）

Product Analyst 是第二个**结构化产出**角色：产品材料（URL/OpenAPI/文档文本）→ ProductModel JSON（SDK `outputFormat` json_schema 同通道，`PRODUCT_MODEL_JSON_SCHEMA` zod 单源生成），平台侧过 `ProductModelSchema` + `validateProductModel` 双校验后**确定性落库**（迁移 0004 knowledge_nodes/knowledge_edges）。

- **逐事实置信标注（验收"无凭空事实"）**：每个事实（Business Entity/User Role/Journey/ApiDependency/StateTransition）必须携带 `confidence ∈ confirmed|inferred|unknown`（复用 ENUM_DICTIONARY.factConfidence）；inferred 事实附 `inferredFrom` 依据；材料回答不了的进 `openQuestions` 而非断言。Schema 层强制，违反即拒绝。
- **合同校验**（validateProductModel）：集合内键唯一（DUPLICATE_KEY）+ 交叉引用完整性——旅程 actor → userRoles（UNKNOWN_ACTOR）、步骤 targetEntity → businessEntities（UNKNOWN_ENTITY）、步骤 apiDependency → apiDependencies（UNKNOWN_API）、迁移 entity → businessEntities（UNKNOWN_TRANSITION_ENTITY）。
- **知识图谱映射**（productModelToKnowledgeGraph 纯函数）：五类节点（business-entity/user-role/journey/api-endpoint/entity-state，externalKey 约定 `<nodeType>:<key>`、实体状态 `entity-state:<entity>:<state>`）+ 四类边（performed-by/covers/calls/transition——DDD §7.2 "边关系值域由应用层定义"的应用层落点）；置信入 properties.confidence（表注释约定）；节点按 externalKey、边按 (source,target,relation) 去重（共享状态跨迁移只落一节点）。
- **memory.* 工具**（@aqaos/mcp）：memory.read_knowledge（memory.read）/ memory.write_knowledge（memory.write）入注册表（目录 27→29）——写侧批内自包含合同（边端点必须在本批节点内，UNKNOWN_NODE_KEY；节点键批内唯一 DUPLICATE_NODE_KEY），pg 实现节点 upsert（UPDATE 回填，0004 无唯一约束）+ 边幂等 + 单事务（Pool 独占 client），应用归属校验（对组织不可见 → NOT_FOUND 防枚举）。
- **prompt v2（迁移 0009）**：product-analyst 产出通道从对话式回答升级为 ProductModel JSON + 置信标注纪律；"先声明后引用"强规则（live 实证：模型引用步骤 API 依赖但漏声明数组——合同校验拦截后由纠偏轮自愈）。种子单一事实源 `productAnalystDefinition()`。
- **会话运行器**（workers/agent product-analyst.ts）：runProductAnalystSession——材料分段组装（URL/OpenAPI/文档）→ 结构化产出双校验 → 确定性落库（图谱映射经 dispatch memory.write_knowledge，product-analyst 角色上下文，权限/预算/审计与 REST 同一调度链；写入不走模型多轮工具调用——概率性写不可审计）。**有界纠偏轮**：首轮违约（schema/合同）→ 第二轮注入违约清单重跑（live 首验场景实证自愈），仍违约带 issues 返回。契约：`model` 存在 ⟺ 双校验通过（写库失败不丢模型）；`issues` 空 ⟺ 已落库。

### 3.7 Test Architect 策略契约（T-E02-09）

Test Architect 是第三个**结构化产出**角色：产品知识（ProductModel，T-E02-07 产出）→ TestStrategy JSON（SDK `outputFormat` json_schema 同通道，`TEST_STRATEGY_JSON_SCHEMA` zod 单源生成），平台侧过 `TestStrategySchema` + `validateTestStrategy` 双校验。策略是纯推理产出（不落库）——由调用方（QA Manager 编排）交给 Test Generator（T-E02-10）与 Run Registry（T-E02-12）消费。

- **测试类型组合**（selections）：每项 = 十二类测试之一（TestSuiteKind/§11 单源）+ 优先级档位（p0/p1/p2）+ 理据（须指向产品特征）+ **focus 键**（journeys/entities/roles 引用 ProductModel 声明集合——"与用例生成衔接"：生成侧按 focus 定向生成）。组合内类型去重（DUPLICATE_TEST_TYPE）。
- **覆盖率目标**（coverageTargets）：dimension ∈ page/endpoint/journey/role/risk（coverage_records 维度对齐）+ targetPercent 0-100；维度去重（DUPLICATE_DIMENSION）、封顶校验（TARGET_EXCEEDS_CAP）。
- **策略可配置**（TestStrategyConfig）：调用方注入允许集（allowedTestTypes）/必选集（requiredTestTypes）/选择数上限（maxSelections）/覆盖目标封顶（coverageTargetCaps）；配置注入会话 prompt（显式约束），平台侧校验违约组合（TEST_TYPE_NOT_ALLOWED/REQUIRED_TEST_TYPE_MISSING/SELECTION_LIMIT_EXCEEDED/CONFIG_CONFLICT）。
- **产品知识对照**（validateTestStrategy 第三参）：提供 ProductModel 时 focus 键悬空即违约（UNKNOWN_JOURNEY/UNKNOWN_ENTITY/UNKNOWN_ROLE）——策略不脱离产品知识（无凭空聚焦）。
- **生成侧消费**：orderedSelections 按档位 p0→p1→p2 稳定排序（同档保持声明序）——Test Generator 的生成顺序单一事实源。
- **prompt v2（迁移 0010）**：test-architect 产出通道从场景矩阵叙述升级为 TestStrategy JSON；"Declare before referencing" 规则（同 Product Analyst 模式）。种子单一事实源 `testArchitectDefinition()`（append-only 第三战，v1 行原样保留）。
- **会话运行器**（workers/agent test-architect.ts）：runTestArchitectSession——知识/意图（PlannerIntent 切片：objective + 建议测试类型）/配置约束分段组装 → 结构化产出双校验（含配置与产品模型对照）→ **有界纠偏轮**（同 Product Analyst：首轮违约 → 第二轮注入违约清单，live 首验断言缺陷为封顶仅约束 journey 维度——其余维度 100% 合法）。契约：`strategy` 存在 ⟺ 双校验全通过；`issues` 空 ⟺ 策略可交给用例生成。

## 4. Agent 详细职责

Agent 团队共 16 个角色（与 SRS 3.1 一致；Mobile Tester 暂缓引入）：QA Manager、Product Analyst、Planner、Explorer、Test Architect、Test Generator、Web Tester、API Tester、Security Tester、Performance Tester、Triage Agent、Bug Verifier、Root Cause Analyst、Regression Agent、Self-Healing Agent、Reporter。

角色按实现形态分三类（与 SRS 3.1 / SDD 6.3 一致）：会话型（纯推理：QA Manager、Planner、Product Analyst、Test Architect、Triage、Root Cause Analyst）；混合型（会话驱动工具：Explorer、Test Generator、Bug Verifier、Self-Healing、Regression、Reporter）；程序型（确定性 Runner：Web/API 执行核心、Security 确定性检查、Performance 测量）。程序型角色不是 Claude Code 会话，LLM 仅用于其结果的事后分析。

所有 Agent 满足第 3 章契约，并具备：动态创建任务、自主调用工具、任务委派、并行执行、根据执行结果调整计划、独立运行状态与预算、暂停/恢复/终止、全程可追踪、支持人工介入和审批。**尽可能减少人工参与，但不能绕过权限、安全和审批边界。**

### 4.1 QA Manager
统筹测试任务和 Agent 团队。接收 Run 目标与预算，维护任务 DAG，分配和调度 Agent，监控进度/成本/异常，处理暂停、恢复和终止，协调 Agent 间委派，触发人工审批。QA Manager 不直接执行测试。

### 4.2 Planner
解析用户目标、加载产品知识、确定平台和测试范围、选择 Agent、估算预算并生成任务 DAG。输出任务需含依赖、优先级、风险和验收条件。

### 4.3 Product Analyst
输入 URL、OpenAPI、产品文档和历史知识；输出 Product Model、Business Entity、User Role、User Journey、API Dependency 和 State Transition。事实必须标注 confirmed/inferred/unknown。

### 4.4 Explorer
流程：初始化队列 → 授权检查 → 导航 → DOM/Accessibility Snapshot → 元素提取 → 页面分类 → 网络观察 → 链接发现 → 去重 → 保存知识和证据 → 继续探索。限制最大页面、深度、时间、费用、频率和域名。探索产出必须是结构化产品知识，不是自然语言总结。

### 4.5 Test Architect
将产品知识映射为测试策略：从 Smoke、Functional、Boundary、Negative、Integration、Regression、Authorization、Security、Performance、Exploratory、State Transition、Compatibility 十二类测试中选择组合，定义覆盖率目标和优先级。

### 4.6 Test Generator
依据测试策略生成具体用例。用例字段：ID、标题、平台、优先级、前置条件、步骤、断言、数据、清理策略、风险、业务模块、覆盖范围、版本。生成前必须对 Memory 去重，避免重复生成已知用例。

### 4.7 Web Agent
Playwright 为确定性执行核心；可选 Stagehand/Midscene Adapter。支持导航、交互、DOM/Accessibility 断言、网络断言、截图、Trace 和 Locator Healing。Locator 优先级：Test ID → Role/Label → Text → CSS → Vision。修复后必须重新断言，不能修改业务预期掩盖产品缺陷。

### 4.8 API Agent
解析 OpenAPI、建立 Endpoint 和依赖图，生成 Schema、边界、负向、认证、授权和 Stateful 测试。Schemathesis 执行 Schema 驱动测试，LLM 负责业务语义分析。请求必须通过目标白名单和速率策略。

### 4.9 Security Agent
确定性检查优先：Security Headers、TLS、CORS、Cookie Flags、认证、授权、敏感信息泄露。主动测试仅限授权资产和获批环境。

### 4.10 Performance Agent
k6 负责负载生成；采集 TTFB、LCP、FCP、CLS、API 延迟、p50/p95/p99、Payload 和 Request Count。Agent 分析指标，不伪造测量值。

### 4.11 Triage Agent
分类七类：`product-bug`、`test-bug`、`environment`、`network`、`flaky`、`model-error`、`unknown`。输入断言、Console、Network、Trace、环境状态和历史失败，输出分类、置信度、证据和建议。不能把测试失败直接当成 Bug；模型误判（model-error）必须显式分类，用于评估 Agent 自身质量。

### 4.12 Root Cause Analyst
输入已分类的失败或已验证 Bug 及其证据链，输出根因假设、证据关联、影响面分析和修复建议。根因结论必须引用证据，不允许凭空推断。

### 4.13 Verifier
必须独立于发现 Agent。加载候选 → 检查环境 → 创建全新会话 → 重放步骤 → 收集独立证据 → 对照业务预期 → 输出 verified/rejected/inconclusive。验证策略按 Bug 类型配置；例如 2/3 复现仅为可配置策略，不是所有问题的统一真值标准。不能只凭模型判断确认 Bug。

```ts
interface VerificationResult {
  bugId: string;
  status: "verified" | "rejected" | "inconclusive";
  attempts: number;
  successfulReproductions: number;
  confidence: number;
  evidenceIds: string[];
  reason: string;
}
```

### 4.14 Self-Healing Agent
负责修复测试脚本和 Locator：重新 Snapshot → 搜索候选 → 评分 → 选择候选 → 独立断言 → 记录旧/新 Locator、策略、置信度和证据。低置信度不得静默替换；修复必须经人工审核后入库，且不得修改业务预期掩盖产品缺陷。连续判定 flaky 的用例移交 Regression Agent 处理隔离。

### 4.15 Regression Agent
从已确认 Bug 生成回归候选，检查已有覆盖、生成脚本、执行验证、版本化；只有通过验证的用例才能进入正式回归集。同时维护 Flaky 隔离（quarantine）策略：隔离用例仍执行但不再阻塞 CI。

### 4.16 Reporter
聚合 Run 结果、Bug、安全、性能、覆盖率、证据和成本，输出 markdown 报告、JUnit XML 和 Dashboard 数据。报告必须可追溯至证据。报告模板可配置；缺陷单推送经 Integration Service（SDD 6.10）执行。

## 5. Workflow 详细设计

### 5.1 主流程
```text
Initialize
 -> ProductAnalysis
 -> Exploration
 -> TestPlanning
 -> ParallelExecution [Web, API, Security, Performance]
 -> EvidenceCollection
 -> Triage
 -> IndependentVerification
 -> RegressionGeneration
 -> Reporting
 -> Completed
```

### 5.2 Temporal 约束
Workflow 只做确定性编排和状态决策。模型请求、浏览器操作、API 请求、文件上传、数据库写入、外部 Issue 创建均放在 Activity。Activity 需要幂等键和超时配置。并行执行采用受限并发和 Child Workflow，不能无限制创建任务。Temporal Schedule 承担定时触发；CI/外部事件经 Webhook 接入创建 Run（trigger.source 标记来源，见 5.6）。

### 5.3 重试策略

| 错误 | 策略 |
|---|---|
| 模型超时 | 有限重试，必要时 Fallback |
| Provider 限流 | 指数退避并遵守 Retry-After |
| 浏览器崩溃 | 重建 Session 后按策略重试 |
| 环境栈启动失败 | 有限重试后置为 failed 并通知 |
| 断言失败 | 不当作基础设施重试 |
| 环境不可用 | blocked 或暂停 |
| 预算耗尽 | 停止新增工作 |
| 未授权操作 | 立即拒绝并审计 |
| 审批超时 | 置 expired，操作拒绝并审计 |

### 5.4 审批流

高风险操作（Production 写入、破坏性请求、支付流程、安全主动测试）触发审批：

- 触发：PreToolUse hook 或策略引擎判定 risk_level ≥ high → 创建 approval_requests，对应 Activity 挂起。
- 路由：按环境策略指定审批人（默认 Project Admin；Production 需 System Admin）。
- 超时：默认 3600 秒，超时置 expired；操作拒绝并审计，Run 按策略继续其余任务或暂停。
- 通知：approval.requested 事件（SSE/webhook/邮件）。
- 约束：触发审批的 Agent 不得自批；决策记录（人、时间、理由）入审计日志。

### 5.5 状态机总览

| 对象 | 状态机 |
|---|---|
| Run | queued → running ⇄ paused / blocked → completed / failed / cancelled |
| 环境栈 | unprovisioned → provisioning → ready → stopped；任一步失败 → failed |
| 测试用例 | draft →（审核）→ active → deprecated；连续 flaky → 隔离（仍执行不阻塞） |
| Bug | candidate → triaging → verifying → verified / rejected → open → fixed → regression_passed / reopened |
| 审批 | pending → approved / rejected / expired |

枚举合法值以 7.3 枚举字典为准。

### 5.6 外部事件回流

外部缺陷单状态变更（Jira/GitHub/GitLab Webhook）更新 external_issue_links；外部标记 fixed/resolved 时自动创建回归验证 Run（trigger.source=event），验证通过后回写提示关单。CI 事件（PR/MR 创建、部署完成）经 /integrations/ci/events 接入，按集成配置触发对应 Run 并回写 commit status / PR check。

## 6. 模型路由

```ts
interface ModelConfig {

  provider: string;
  modelId: string;
```

路由请求：
```ts

  taskType: string;
```

路由步骤：任务分类 → 能力过滤 → 数据策略校验 → Provider 健康检查 → 预算检查 → 选择模型 → 请求 → 输出 Schema 校验 → 记录 Token/成本/延迟 → 有限 Fallback。模型名称必须配置化，不能硬编码在 Agent 业务逻辑中。

Claude Code 会话的模型流量经 Anthropic 兼容端点代理接入 Model Gateway，统一计量、审计与限流；也可直连 Anthropic API / Bedrock / Vertex。Agent 推理默认使用 Claude 系列；其余任务按路由规则选择 Provider。

## 9. MCP Tool 设计

MCP 域：qa-control、browser、api-testing、environment、evidence、memory、security、performance。

平台 MCP Server 服务两类消费者：Claude Code Agent（经其原生 MCP 客户端）与外部集成（REST/API）。Claude Code 客户端工具白名单（allowedTools）是第一层限制，服务端身份、权限与预算校验是最终强制层。

QA Control：`qa.create_run`、`qa.get_run`、`qa.cancel_run`、`qa.get_coverage`、`qa.list_bugs`。

Browser：`browser.navigate`、`browser.snapshot`、`browser.click`、`browser.fill`、`browser.observe`、`browser.act`、`browser.screenshot`、`browser.network_log`。

API：`api.get_schema`、`api.request`、`api.run_schema_test`、`api.run_fuzz_test`、`api.inspect_response`。

Environment：`env.list_environments`、`env.get_status`、`env.provision`、`env.health_check`、`env.teardown`。

Evidence：`evidence.save`、`evidence.get`、`evidence.search`、`evidence.generate_report`。

每次 MCP 调用必须验证 Agent 身份、Run ID、应用授权、工具权限和预算。权限示例：Explorer 可读写浏览器并写证据；API Agent 可执行 API 测试；Reporter 只读测试结果和证据；Verifier 仅在获批环境执行复现。

### 9.1 Tool Server 基座契约（V1.9 增补，T-E02-03）

实现：`packages/mcp`（`@aqaos/mcp`，传输无关核心）+ `workers/agent/src/mcp-server.ts`（SDK 进程内适配）+ `apps/api`（REST 路由与 pg 服务）；权限矩阵为 domain 0.4.0 `mcp-tools.ts`（单一事实源，T-E11-05 RBAC 定稿时统一收口）。

- **权限粒度**：`<domain>.<read|write|execute>`；工具目录（`MCP_TOOL_SPECS`，30 个 canonical 点分名）+ 16 角色授权表（`ROLE_TOOL_GRANTS`，支持 `<domain>.*` 与 `*.read` 通配）+ 判定函数 `grantsAllow` 全部在 domain 层纯数据/纯函数。
- **调用链中间件**（`dispatchToolCall`，双消费唯一入口）：注册表解析（canonical 与 SDK 下划线名双索引）→ zod strict 输入校验 → 权限判定（denied `TOOL_PERMISSION_DENIED` 并审计）→ 预算钩子（T-E02-13 接 model_invocations 扣减，基座缺省放行）→ 执行（处理器异常收敛为结构化 failed，不泄漏堆栈）→ 终态审计。dispatch 永不向上抛异常。
- **可信上下文构造**（`context.ts`）：`agent-session` 上下文由 workers/agent 从已验证 agent_runs 行构造（组织/角色/Run 绑定来自数据库）；`rest` 上下文由路由从已验证 JWT+成员关系构造。REST 阶梯：viewer 零工具、member 全域只读、admin/owner 全权（`*`）。
- **双消费**：SDK 侧 `createAqaosSdkMcpServer`（`createSdkMcpServer` 进程内实例，工具名点分→下划线 `qa.get_run`→`qa_get_run`，经 `Options.mcpServers` 顶层选项注入，会话内 `mcp__aqaos__<tool>`）；REST 侧 `POST /api/v1/mcp/tools/:toolName`（denied→403/429，failed→400/404/500 统一错误体）。
- **审计语义**：调度链每次终态（denied/succeeded/failed）各落一条 audit_logs（action `denied`/`execute`，resource_type `mcp-tool`，metadata 含工具名/来源/角色/Run 绑定，绝不记录工具载荷）；审计写失败不改变调用结果。
- **基座工具集**：qa.get_run / qa.list_bugs / qa.get_coverage / env.list_environments / memory.read_knowledge / memory.write_knowledge / memory.search_memories（pg 实现按 organization_id 过滤，组织不匹配表现为 NOT_FOUND/空集防枚举）；输出为投影类型（`McpRunSummary` 等），其余 23 个目录工具随 E04-E07 引擎落地登记。

### 9.2 Memory 基座契约（V1.15 增补，T-E10-01）

跨 Run 记忆（§7.2 memories 表）的读写契约与嵌入接缝——**查询强制租户过滤**的落地形态：

- **隔离合同**：MemoryRecord 携带 scope 三键（organization/project/application）；`MemorySearchQuerySchema` 将 `organizationId` 定为**必填首键**，检索 SQL 的 WHERE 首条件恒为 `organization_id = $1`（值取自可信上下文，用户输入只提供收窄键）——跨组织检索在构造上不可能，验收"记忆查询强制租户过滤"。
- **检索语义**：pgvector cosine 近邻（`ORDER BY embedding <=> $query`，HNSW 索引 0011 `vector_cosine_ops`；未嵌入行 NULL 自动跳过）；score = `1 - distance`；过期记忆（expires_at）检索侧过滤不物理删除；kind 五类收窄（ENUM_DICTIONARY.memoryKind）。
- **嵌入接缝**（`EmbeddingClient`）：embed(texts) → 向量；过渡期 `HashEmbedder`（QA-Swarm 同款 sha1 分桶符号哈希，1536 维对齐 DDL，确定性——同文本永远同向量，去重判定可重复）；T-E04 模型网关落地后换真实嵌入实现，维度变更走迁移复核。**pg 参数形态 gotcha：向量须 JSON.stringify 后 `::vector` 传文本 '[...]'——直接传 JS 数组被驱动序列化成 '{...}' Postgres 数组导致转换失败。**
- **工具面**：`memory.search_memories`（memory.read）入注册表（目录 29→30）——输入只有 query/收窄键/limit，组织取上下文；输出投影不含 organizationId（冗余）。平台确定性写 API `insertMemory`（apps/api 内部服务面，不经 MCP 工具暴露——与知识图谱同律：写是平台行为非模型行为）。

## 10. Web 执行引擎

BrowserSession 字段：id、runId、applicationId、environmentId、browserType、status、startedAt。

浏览器矩阵：Chromium、Firefox、WebKit（Safari 内核）。Smoke 用例默认仅 Chromium；Compatibility 用例在矩阵全浏览器执行；矩阵并发受 Browser Slot 限制，调度按「用例数 × 浏览器数」预算 Slot。

执行流程：Acquire Slot → Validate URL → Create Isolated Context → Inject Credential Reference → Execute Steps → Capture DOM/Network/Console → Screenshot/Trace → Upload Evidence → Close Context → Release Slot。

Locator Healing：重新 Snapshot → 搜索候选 → 评分 → 选择候选 → 独立断言 → 记录旧/新 Locator、策略、置信度和证据。低置信度不得静默替换。

## 11. API 执行引擎

OpenAPI Parser 输出 Endpoint、method、path、operationId、parameters、requestSchema、responseSchemas、tags。

Pipeline：Load Spec → Parse → Build Dependency Graph → Generate Schema/Boundary/Negative Cases → Execute → Validate Status/Schema/Business Assertions → Collect Evidence → Triage。

必须实施域名白名单、凭据隔离、速率限制、请求体大小限制、并发限制、破坏性请求审批和敏感数据脱敏。

## 12. 环境管理引擎（Docker Compose）

Environment 支持两种供给方式：external（外部已有服务，仅配置 URL）与 docker-compose（由平台编排拉起被测应用栈）。

Compose 环境配置：composeFileRef（对象存储/仓库引用）、variables（模板变量）、healthCheck（path/timeout/interval）、resourceLimits（CPU/内存上限）、credentialRefs（凭据引用，注入容器环境变量，不落盘、不进日志）。

生命周期状态机：`unprovisioned → provisioning → ready → stopped`；任一步失败进入 `failed` 并保留诊断日志。

流程：解析 Compose → 校验镜像与网络出口白名单 → 渲染变量 → 注入凭据 → `docker compose up -d` → 健康检查轮询（就绪前不进入测试）→ 标记 ready → 执行 Run → down 或保留。支持数据播种（seed 脚本）与重置（重建栈或清库）；Run 可声明执行前重置。

约束：

- 同一环境同时仅允许一个活动栈（Redis 互斥锁）。
- Run 调度前必须确认环境 ready；环境 failed 时 Run 进入 blocked。
- Production 环境禁止平台拉起与销毁。
- 资源限额与清理策略防止栈残留。

## 13. 测试用例管理

用例生命周期：`draft → reviewed → active → deprecated`。AI 生成用例默认 draft，人工审核通过后转为 active 才能进入执行计划与正式回归集。

维护能力：

- 版本管理：每次修改生成新版本（test_case_versions），可查看差异与回溯历史。
- 来源标记：created_by 标记 ai / human，修改记录操作者。
- 启用/禁用与标签：禁用用例不再进入执行计划；支持平台/类型/业务模块/标签筛选。
- flaky 标记：连续判定 flaky 的用例进入隔离（quarantine），仍执行但不阻塞 CI。
- 关联追溯：用例与 Run 结果、Bug、回归集成员关联，可查询"某 Bug 由哪些用例覆盖"。
- 导入导出：JSON/CSV 格式，用于迁移与评审。
- 数据集引用：用例引用 data_sets（业务实体样本与边界值集合），Boundary/Negative/Authorization 用例消费数据集变体；数据集变更触发受影响用例重审。

用例与执行脚本契约：

- test_cases 是唯一事实源；脚本（Playwright spec / Schemathesis 配置）由 Test Generator 从用例渲染生成，存对象存储，以 script_ref + script_fingerprint 绑定。
- 同一用例可对应多个脚本（不同浏览器/环境）；执行结果同时记录用例 ID 与脚本指纹，双向可追溯。
- 用例升级版本后旧脚本自动失效，需重新生成并通过验证；脚本手工修改必须回写用例并升版本，否则标记 drift 并阻止进入回归集。

REST 接口见第 8 章 /test-cases；Dashboard Test Case Library 页面提供列表、筛选、详情、版本历史与审核操作。

## 16. 异常模型

错误码：APPLICATION_NOT_FOUND、ENVIRONMENT_UNAVAILABLE、ENVIRONMENT_PROVISION_FAILED、MODEL_UNAVAILABLE、MODEL_BUDGET_EXCEEDED、AGENT_TIMEOUT、TOOL_PERMISSION_DENIED、BROWSER_CRASHED、NETWORK_POLICY_BLOCKED、EVIDENCE_UPLOAD_FAILED、WORKFLOW_FAILED、APPROVAL_REQUIRED、APPROVAL_EXPIRED、WEBHOOK_DELIVERY_FAILED、ISSUE_SYNC_FAILED、CI_EVENT_REJECTED。

### 16.1 传输层错误码（V1.4 增补，T-E01-08）

控制面 REST 层在 16 个域错误码之外引入 9 个传输层错误码，统一进入 §8.1 错误信封 `{ error: { code, message, requestId, details? } }`，HTTP 状态映射固定（实现：apps/api/src/lib/errors.ts）：

| 错误码 | HTTP | 语义 |
|---|---|---|
| VALIDATION_FAILED | 400 | 请求体/参数违反 schema；details 携带校验明细数组 |
| NOT_FOUND | 404 | 路由或资源不存在（路由级由统一 404 处理器生成） |
| IDEMPOTENCY_KEY_REQUIRED | 400 | 路由声明 requireIdempotencyKey 但请求缺 Idempotency-Key 头 |
| IDEMPOTENCY_KEY_REUSED | 409 | 同键不同载荷（键是一次性的，Stripe 语义） |
| AUTHENTICATION_REQUIRED | 401 | 未认证（T-E01-09 接入后生效） |
| PERMISSION_DENIED | 403 | 已认证但无权限（RBAC，T-E01-09/T-E11-05） |
| PAYLOAD_TOO_LARGE | 413 | 请求体超过 bodyLimit（1 MiB） |
| INTERNAL_ERROR | 500 | 未知服务端错误（日志带堆栈，响应不泄漏内部细节） |
| NOT_IMPLEMENTED | 501 | 契约已定义、实现未落地的诚实占位（如 POST /api/v1/runs → Run Registry T-E02-12） |

幂等语义（§8.1 创建 Run 的落地约定）：键作用域 = 方法 + 路由模板 + 键值；同键同载荷重放缓存响应并回写 `x-idempotent-replay: true`；5xx 不缓存（客户端可安全重试）；一阶段为进程内存储，并发 in-flight 同键去重随 M2 Redis 存储补齐。所有响应（含错误）回写 `x-request-id`，错误体 requestId 与之一致；入站 x-request-id 合法（≤128 字符、`[A-Za-z0-9._-]`）则透传，否则生成 UUID（防日志注入）。

审计留痕约定（T-E01-11 落地，实现：apps/api/src/plugins/audit.ts + lib/audit.ts）：变更类请求（POST/PUT/PATCH/DELETE）在 onSend 钩子按纯函数规则推导事件——2xx 映射 create/update/delete、RBAC 403 映射 denied（"未授权操作立即拒绝并审计"）；GET 等读操作与 401/400/404/5xx 不留痕；仅审计 `/api/v1/` API 面。写入为 fire-and-forget 旁路（留痕失败仅记日志，绝不影响响应）；单请求经 WeakSet 去重只留痕一次。metadata 仅含 requestId/method/route/statusCode——**请求体绝不入审计**（密码/凭据类载荷防泄漏），完整登录审计（无组织上下文的 actor-only 行）随 T-E11-05 用户级审计目标补齐。查询经 GET /audit-logs（minRole admin），action 取 create/update/delete/denied。

## 22. 架构决策记录（ADR）

- ADR-001：复用 QA-Swarm TypeScript 核心。
- ADR-002：模块化单体 + 独立 Worker。
- ADR-003：Temporal 管理长任务持久化。
- ADR-004：Agent 推理循环由 Claude Code（Claude Agent SDK）承担；LangGraph 仅作 QA-Swarm 过渡兼容层。
- ADR-005：LiteLLM + 自建 Model Router。
- ADR-006：向量检索用 PostgreSQL pgvector（**Qdrant → pgvector 迁移决策**，T-E10-01 补充理由）：① 租户过滤与近邻检索在同一条 SQL 强制（`WHERE organization_id = $1 ORDER BY embedding <=> $q`）——无跨库同步窗口、无不一致隔离语义；② 记忆规模（每应用千级、HNSW 索引）下延迟够用，独立向量库的运维/连接池/备份成本不成立；③ 与 DDD §7 数据面统一（备份/RLS/审计一套机制）。QA-Swarm 遗留 Qdrant 代码（packages/core VectorStore 适配层）不迁移，平台以 memories 表 + pg 实现重写。变更条件：单应用记忆达 10⁷ 级或需要多向量混合检索（重排序/稀疏+稠密）时重新评估独立向量库。
- ADR-007：MinIO 保存证据。
- ADR-008：Playwright 作为 Web 确定性执行核心。
- ADR-009：Schemathesis 作为 API Schema 测试核心。
- ADR-010：独立 Verifier 是 Bug 确认的必要环节。
- ADR-011：Agent/Tool 必须有权限和预算。
- ADR-012：任务必须可追踪和恢复。
- ADR-013：高风险操作默认人工审批。
- ADR-014：记忆按应用和项目隔离。
- ADR-015：自主性按 L1–L5 分级演进；即使达到 L5 也不绕过权限、安全与审批边界。
- ADR-016：产品按 11 个核心业务模块组织，Agent 团队为 16 角色契约（见 SRS 3.1）；Mobile 测试暂缓。
- ADR-017：测试环境支持 Docker Compose 应用栈编排；Production 环境只读，不允许平台拉起。
- ADR-018：Agent 执行层基于 Claude Code / Claude Agent SDK；工具经 MCP Server 接入；审批/权限/沙箱采用客户端 + 服务端双层，服务端为最终强制层。
