## 1. 设计原则

1. 最大化复用 QA-Swarm 已有稳定业务逻辑。
2. 采用模块化单体 + 独立 Worker，避免过早微服务化。
3. Agent 负责智能决策，Runner 负责确定性执行。
4. Temporal 负责长任务持久化和恢复；Agent 推理循环由 Claude Code（Claude Agent SDK）承担，LangGraph 仅作为 QA-Swarm 过渡期兼容层。
5. PostgreSQL 是业务事实数据源；MinIO 保存大对象证据。
6. 所有模型调用经统一 Model Gateway。
7. 所有 Tool Call 必须有身份、权限、预算和审计。
8. 记忆按 Organization/Project/Application 隔离。
9. 自主性按 L1–L5 分级演进（见 SRS 第 6 章）；高自主性不得绕过权限、安全与审批边界。
10. 产品按 11 个核心业务模块组织（Agent 管理中心、自主探索引擎、测试设计中心、Web/API 测试引擎、安全测试中心、性能测试中心、Bug Intelligence、QA Memory、Model Gateway、QA Analytics；Mobile 测试引擎暂缓），模块间通过领域契约集成，不做成 Agent 简单拼接。
11. 测试环境支持 Docker Compose 应用栈编排，平台负责生命周期与健康检查；Production 环境只读，不允许平台拉起。
12. Agent 执行层基于 Claude Code / Claude Agent SDK：角色 = 系统提示词 + MCP 工具白名单 + 模型配置；委派用子代理；高风险操作用 hooks + 平台策略双层拦截（服务端为最终强制层）；沙箱与 Worker 容器隔离叠加。

## 6. 核心模块设计

### 6.1 Identity
负责身份认证、RBAC、组织成员、API Token、审计。权限至少按 Organization、Project、Application、Environment 逐级约束。支持 OIDC（飞书/企业微信/Google 等）与 LDAP 单点登录（SRS FR-030），本地账号兜底。

### 6.2 Application & Environment Registry
维护 Project、Application、Environment、Platform、Target URL、OpenAPI、Credential Reference 和 Network Policy。Platform 当前支持 web 与 api（Mobile 暂缓）。

Environment 支持 external（外部已有 URL）与 docker-compose（平台编排）两种供给方式。Compose 环境绑定 compose 文件引用、变量模板、健康检查与资源限额；Environment Worker 负责 up/down/重启、健康轮询、状态机（unprovisioned/provisioning/ready/failed/stopped）与并发互斥（同一环境同时仅一个栈）。凭据以引用注入，不落盘、不进日志。Production 环境只读，不允许平台拉起。

### 6.3 Agent Runtime（基于 Claude Code）
Agent 执行层基于 Claude Code / Claude Agent SDK 实现。每个 Agent Run 对应一个 SDK 会话（headless 运行于 Agent Worker 内）：

- **角色定义**：`agent_definitions` 的 prompt_version 与 config 映射为会话系统提示词、MCP 工具白名单（allowedTools）和模型配置。
- **工具接入**：平台工具以 MCP Server 形式暴露（browser、api-testing、environment、evidence、memory、qa-control），由 Claude Code 原生 MCP 客户端调用；权限由服务端强制校验，客户端白名单仅为第一层。
- **任务委派**：QA Manager 通过 SDK 子代理（subagent）或 Temporal 子工作流把任务委派给其他 Agent。
- **审批与权限**：PreToolUse hook 拦截高风险工具调用并转交平台 approval_requests；服务端策略优先于客户端配置，Prompt Injection 不能覆盖权限边界。
- **沙箱**：Claude Code 沙箱 + Worker 容器隔离 + 网络出口白名单三层叠加。
- **用量与预算**：SDK usage 回调统一上报 Model Gateway 计量，计入 Run 预算。
- **生命周期**：暂停/恢复/终止由 Temporal 控制 SDK 会话中断与续跑。

Agent 输出必须符合统一 Schema，校验失败按部分成功处理。LangGraph 仅作为 QA-Swarm 过渡期兼容层保留。

Agent 三分类（16 角色不全部会话化，避免 Token 浪费与不可控）：

| 类型 | 实现方式 | 角色 |
|---|---|---|
| 会话型 | 纯推理决策，完整 Claude Code 会话 | QA Manager、Planner、Product Analyst、Test Architect、Triage、Root Cause Analyst |
| 混合型 | 会话驱动 MCP 工具，关键动作结构化输出 | Explorer、Test Generator、Bug Verifier、Self-Healing、Regression、Reporter |
| 程序型 | 确定性 Runner（LLM 仅事后分析） | Web/API 执行核心、Security 确定性检查、Performance 测量 |

### 6.4 Workflow Engine
Temporal 管理 Run 生命周期、Activity、并行任务、重试、超时、暂停、取消、恢复和审批。Agent 推理循环由 Claude Code 会话承担（作为 Activity 执行）；LangGraph 仅作过渡兼容层。外部副作用必须放在 Temporal Activity 中。Temporal Schedule 承担定时触发（nightly/周期全量）；CI 与外部事件经 Webhook 接入创建 Run，触发源（manual/schedule/event/ci）全程可追溯（SRS FR-026）。

### 6.5 Model Gateway
```text
Agent -> ModelRouter -> TaskClassifier -> CapabilityFilter
      -> DataPolicy -> Budget/CostLimiter -> LiteLLM -> Provider
```
提供 Provider Registry、Model Registry、能力过滤、成本统计、超时、重试、Fallback、Circuit Breaker、Structured Output 校验和调用审计。

任务与模型能力映射（路由必须按任务类型自动选择，不允许只配置单一默认模型）：

| 任务类型 | 模型能力要求 |
|---|---|
| 简单页面分类 | 低延迟模型 |
| 页面和业务理解 | 强推理模型 |
| 测试用例生成 | 推理 + 结构化输出 |
| 页面截图分析 | Vision 模型 |
| Bug 根因分析 | 强推理模型 |
| 报告生成 | 高性价比模型 |
| 向量记忆 | Embedding 模型 |

支持 Provider：OpenAI、Anthropic、Gemini、DeepSeek、Qwen、Ollama、vLLM 及 OpenAI-Compatible Provider。

路由决策必须综合考虑能力、延迟、价格、可用性、数据敏感级别和预算，而不是只选择最便宜的模型。模型名称必须配置化，不允许硬编码在 Agent 业务逻辑中。

**硬性交付要求：Model Gateway 必须实现 Anthropic Messages 协议兼容端点**（自研适配层，或验证过的 LiteLLM Anthropic 兼容层），供 Claude Code 会话接入，统一预算、审计与限流。端点不可用时降级为 Agent Worker 直连 Anthropic API / Bedrock / Vertex，但该流量脱离统一治理，必须告警并在 model_invocations 中标记。Agent 推理默认使用 Claude 系列；其他 Provider 承担 Embedding、简单分类、报告等非 Agent 任务，或数据敏感场景的本地模型任务。

### 6.6 Execution Service
统一接口：
```ts
interface ExecutionAdapter {
  createSession(context: ExecutionContext): Promise<ExecutionSession>;
  execute(session: ExecutionSession, task: ExecutionTask): Promise<ExecutionResult>;
  captureEvidence(session: ExecutionSession): Promise<EvidenceReference[]>;
  closeSession(session: ExecutionSession): Promise<void>;
}
```
实现 Playwright、Stagehand、Midscene、Schemathesis、Docker Compose（环境栈）Adapter。

### 6.7 Memory Service
- Product Memory：页面、业务实体和流程。
- Exploration Memory：探索路径和状态。
- Test Memory：测试用例及结果。
- Bug Memory：历史缺陷和根因。
- Feedback Memory：人工反馈。
- Vector Memory：向量检索。

每条记忆携带 organization_id、project_id、application_id、source_run_id、version、confidence、created_at 和可选 expiry_at。

Feedback 闭环：人工标记误报/确认进入 Feedback Memory，结合 Golden Dataset 定期评测，驱动提示词与路由调整（SRS FR-028）。

### 6.8 Evidence Service
统一保存 Screenshot、Video、Playwright Trace、HAR、Console/Network Log、API Request/Response 和报告。Agent State 只存 evidence_id 和元数据，不存 Base64 大文件。

### 6.9 Test Case Management
维护测试用例库：用例生命周期（draft → reviewed → active → deprecated）、版本历史与差异、AI 生成用例人工审核、启用/禁用、标签与 flaky 标记、与 Run 结果和 Bug 的关联、回归集成员管理和导入导出。用例变更必须记录来源（AI 生成/人工编辑）。

测试数据管理：数据集定义业务实体样本（账号、订单、边界值集合），用例引用数据集；环境支持数据播种与重置（栈重建或 seed 脚本）（SRS FR-029）。

### 6.10 Integration Service
统一出口集成：缺陷单（Jira/GitHub Issues/GitLab）、CI 状态回写（commit status / PR check）与通知渠道。集成配置与凭据引用集中管理（external_integrations），调用有限重试并审计；事件（issue.synced、issue.status_changed）进入统一事件流；外部状态回流（fixed）自动触发回归验证 Run（SRS FR-026/027）。

## 7. 数据架构

PostgreSQL 存业务实体和结果；pgvector 存向量；MinIO 存文件；Temporal 使用独立持久化数据库或独立 Schema。Temporal 内部表不与业务表混用。

核心实体清单与 DDL 以《详细设计说明书》§7 为单一事实源（33 张核心表，含枚举字典 §7.3），本文档不重复维护，避免双写失同步。

## 8. 安全架构

### 8.1 网络
- Browser/API Worker 仅访问授权资产。
- 禁止云元数据地址和未授权内网网段。
- DNS 解析后校验 IP；每次 Redirect 重新执行策略。
- 限制端口、协议、请求速率和响应体大小。
- 不允许用户任意注入代理配置。

### 8.2 Secret
- Secret Manager 或加密存储。
- 不写入 Prompt、日志或普通 Run State。
- 按组织/项目/环境授权。
- 支持轮换和撤销。

### 8.3 Agent
- Tool Allowlist。
- Agent 身份和 Run 绑定。
- 时间、Token、费用和并发限制。
- 高风险操作分级审批。
- Prompt Injection 不能覆盖服务端权限策略。

### 8.4 数据隔离
PostgreSQL RLS + 服务端授权；对象存储采用受控 Bucket/Prefix；向量查询必须强制附带租户和应用过滤条件。

### 8.5 数据出境与模型调用
被测应用内容（截图、DOM、网络响应、日志）会进入模型上下文，必须分级管控：

- 数据分级：public / internal / confidential，与 ModelRoutingRequest.dataSensitivity 一致。
- confidential：强制路由本地模型（Ollama/vLLM）；无可用本地模型时任务置为 blocked，不允许降级出境。
- internal：允许出境到显式配置的 Provider；Secret 永不出境，进入 Prompt 前脱敏。
- 出境脱敏：已知 PII 模式（邮箱、手机号、Token）在进入上下文前掩码，规则可配置。
- 出境审计：model_invocations 记录任务类型与数据级别，供合规回溯。
- 默认级别 internal，可在环境级覆盖。

## 9. 可观测性与运维

采用 OpenTelemetry 统一 Trace、Metrics、Logs。关键指标包括 Run 状态、Agent 时长、Activity 重试、Worker 利用率、Browser Slot、环境栈状态、模型 Token/成本/延迟、证据上传失败率和 Bug 验证率。

必须提供数据库备份、对象存储备份、Migration 回滚策略、密钥轮换、日志脱敏和数据保留策略。

## 10. 扩展策略

第一阶段模块化单体 + Worker；第二阶段独立扩容 Agent/Web/API/Environment Worker；第三阶段根据瓶颈拆分 Model Gateway、Evidence、Memory 等服务。不得仅因架构图而提前拆微服务。
